# 28.0 ID families

**Rule:** Every identifier family answers three questions in one place: where a value is *defined*, what scope it must be *unique* in, and how the next one is *minted*. One row per family; a new family adds its row here at creation instead of improvising - the triad is cheap to fill while the thinking is hot and expensive to reconstruct after drift. (DataWizard, 2026-08)

| Family | Format | Definition site | Minting rule | Uniqueness scope |
|---|---|---|---|---|
| Session IDs | `SNNN` (solo) / composite (multi-operator) | session log section folder (claim stub) | optimistic claim: next free above highest entry and any in-progress stub | project |
| Decision IDs | `DNN` | decision log entry | next sequential; never reused - supersede instead | project |
| Open questions | `QNN` | decision log open questions | next sequential | project |
| Thread IDs | `TNN` | Active Threads ledger row | next free on arc open | project |
| Gate IDs | `G-NNN` | Operator Gate Queue row | next free at queue feed | project |
| Quest IDs | `XX-Q-NNN` | quest file frontmatter (`quest_id`) | next free across active quests + archive | project |
| Task IDs | `PREFIX-NNNNN` | checkbox line in the quest layer | scan-max + verify-after-mint - see the **Quest Lifecycle** protocol (canonical home) | project (scan scope = active quests + archive + quest index) |
| Intake titles (FRs, bug reports) | descriptive filename | the intake folder | filename uniqueness; descriptive, not coded | intake folder |
| Holon ids (`hid`) | 20 chars from `a-z 2-7` | core note frontmatter | minted by the holon index when a core lacks one (one-time reconciliation may copy a pre-existing consumer id first); cryptographic random; never derived from a name; never reissued or re-keyed | global - every vault, store and consumer |
| Core ids (`core_id`) | kebab-case slug | core note frontmatter | written by the federating skill or its batch twin from the name at core creation; stable forever once written; a merge keeps both | vault |
| Relation ids | derived, not stored: 20 base32 chars of sha256 over `subject hid|pred|target|role|since` | holon index | computed from content, never from list position | global |
| Board row IDs | `B-NNNN` (one number space for claims and for asks of either `intent`) | board table in the operational db, mirrored in the board files (`_Coordination/Board.md`, `Inbox/`, `Board Archive/`) | script: next above the highest id in the table and every board file; by hand: `next_free`, or the next id above the highest present (index incl. Unreconciled, inboxes, archive) if that is higher; re-read, renumber on collision | vault |
| Harvest point ids (pilot) | `h<YYMMDD>-NNN`; a second call the same day adds a letter to the date part (`h261120b-001`); numbers below 1000 have three digits; above that, as many as needed | the transcript's frontmatter: whoever files the transcript writes `point_id_prefix:`, and each project's block is claimed there; each id is a block id on its point in that project's harvest note | within the project's claimed block: above the highest id minted in that block, counting retired ids. Before a project's first id on a call: if the transcript has no prefix, write it; if the project holds no block with room left, claim the next free block above the highest block claimed; re-read to confirm the claim. On re-read, if another line holds the same range, the line that comes later in the list moves to the next free block and re-reads again. | vault |

The Task IDs row is the worked example: its definition-site / scope / minting triad took a three-session design arc to settle after live collisions in two projects; filling the row at family creation is the cheap alternative.

The Harvest point ids row is a pilot. One call has one id space, kept on the transcript. Each project that harvests the call claims its own block of numbers there and mints only inside it, so two harvests of one call never mint the same id. A point has one id and one home; another project cites it and does not copy it. A retired id stays in its harvest note as a line marked retired, so a scan for the highest id still finds it. A planted passage (a passage in a document that carries a point) cites its point with a normal block citation (11.0); a passage gets its own `^bN` only when something cites it. A point id is a name, not a date: it does not change when a call's date is corrected. (DataWizard, 2026-11)

The block field is `point_id_blocks:`. It is a list on the transcript, one line per block, each with `project` and `range`. The `project` value is the project's name in full. Blocks are fixed ranges: 001-999, then 1000-1999, 2000-2999, and so on. A project may hold more than one line. For example:

```yaml
point_id_prefix: h261120
point_id_blocks:
  - project: <project name>
    range: 001-999
  - project: <project name>
    range: 1000-1999
```

The owner of a point is the harvest note that holds it. The block line only says who makes the next numbers. If a block's points later sit in two projects, no id changes. (DataWizard, 2026-11)

**Example:** a new "experiment IDs" family gets its row (format, definition site, minting rule, scope) before the first ID is minted.

# 26.0 Coordination board

**Rule:** Cross-project asks and write-claims live on one vault-level board, read at every project's orientation (sweep sub-check (d)) and written when each outbound item is written, with the close-time cross-project write check as the safety net (it posts any missing ask; held claims are released). A board row is a pointer - `hid:`, `path:`, `store:` or `project:` - plus one summary line; the content stays in the exchange note, feature request, gate row or core it points at. Claims are coarse (a store, a subtree, a holon), carry a TTL and a heartbeat, and are refused by every owning-project script while another live claim covers the target. Action asks never expire automatically; the target project rules them done, declined or stale. Awareness asks lapse after 30 days (below). The table in the operational db is the atomic store; the markdown board files (below) are the durable shared record; terminal rows rotate monthly to an archive and are never deleted. This is the reader-side artifact the "rows count as outbound items" rule requires, provided once for every project instead of once per note. (DataWizard, 2026-10; D135.)

**Example:** a session files a pickup note in another project's Session Exchange and, in the same step, posts `B-0007 ask - to: that project - note: <the note's path>`; that project's next orientation lists it in the first five lines it reads.

**Post at write time.** Post the ask in the same step that writes the outbound item (an exchange note or feature request to another project) - not only at close. A session that ends without a full close (lite close, compaction, crash, a long-running thread) otherwise leaves a note no project sees at orientation. The close-time cross-project write check stays as the safety net: it verifies that each outbound item has a row and posts only the missing ones. (Community Stack, 2026-10)

**Gate rows point at their ask.** When a gate row (Operator Gate Queue) waits on an ask, the row carries `- ask: B-NNNN`, and the ask may end its summary with `[G-NNN]`. Then a script can tell when the ask closes, and the row does not keep saying "pending" after the other project is done. (DataWizard, 2026-10)

**Awareness asks.** An ask may carry `intent: action | awareness` (default `action`; a block without the field is an action ask). An `awareness` ask says "I changed something you build on; nothing is asked": it points at the changed note or its decision entry, and its statuses are open -> seen | stale (no picked-up, no done). The target project marks it seen as an explicit act at orientation or close (below). `stale` means superseded, withdrawn by the poster, or lapsed. Post one, per affected project (or `all`), when a session changed something another project depends on - a shared vocabulary, a protocol, schema or design doc another project cites, a data contract, a decision another project built on - without asking that project to act. If the other project must do anything, it is an action ask, not awareness; tool-behavior notes the receiving project will plant are `intent: action`. No third block kind: awareness asks share the ask grammar and the `B-NNNN` number space. The orientation trace gains a `K awareness` count at the next Project Instructions bump, not before. (Holonic Canvas proposal, DataWizard ruling, 2026-10)

**Seen by several projects.** An awareness ask to one project closes when that project sets `status: seen` and `updated`. An ask to two or more named projects, or to `all`, carries a `- seen_by:` line: the abbreviations of the projects that have seen it, comma-separated. On such an ask, a project marks it seen by adding itself to `seen_by:` and setting `updated` (by hand), or with the board script's `seen` command. It does not set `status: seen` there: the render refuses that status change but keeps the rest of the edit (the seen_by entry too), reports the refusal once and writes the block back as open. The render closes an ask to named projects as `seen` once every named project is in `seen_by`. An ask to `all` never closes as seen - only by lapse, or when its poster withdraws it as `stale`. Orientation hides an ask whose `seen_by` already holds this project (Query Spec, sub-check (d)). (DataWizard, 2026-11)

**Awareness asks lapse after 30 days.** An open awareness ask lapses at the first render 30 days after its `posted` time. The clock is `posted`, not `updated`, so one project's seen mark does not restart it for the others. The ask becomes `stale` with a `closed` time and a resolution, the audit log records a `lapse` event, and the row rotates to the archive like any closed row. The resolution says who saw it: `lapsed unseen after 30 days` when `seen_by` is empty; otherwise `lapsed after 30 days; seen by <seen_by>`, plus `; not seen by <the named projects missing>` on an ask to named projects (an ask to `all` gets no such list). An earlier resolution is kept at the end as ` (was: <old>)`. The same text goes into the row, the archive block and the audit event. Action asks never lapse: if a receiving project must still do something, post an action ask before the 30 days run out. (DataWizard, 2026-11)

**The board files.** The shared record is an index, one inbox per project and the archive, all in the board folder. The index `Board.md` carries `next_free`, the hand-path header, a count line per project, and under `## Live` the asks to two or more projects or to `all`, every claim, and hand posts not yet rendered. An inbox `Inbox/<ABBR>.md` carries under `## Live` the asks addressed to that project alone. Each block lives in one file: the render places it by its `to:` list (one project: that inbox; two or more, or `all`: the index) and moves it when `to:` changes - a hand edit of `to:` also sets `updated`, or the table wins and the block goes back. **One posting point:** a hand post goes at the end of the index `## Live`, never into an inbox; edit a block in the file where it is. A refused block goes to the `## Unreconciled` section of its own file. When one block number is in two files, fold takes the newer `updated`; on a tie the order is the index, then `Inbox/*.md` by name, then the archive. The archive is `Board Archive/YYYY-MM.md`, continued past about 40 KB in parts `YYYY-MMb.md`, `YYYY-MMc.md`, ... (new rows go to the newest part; a later part wins a tie). `## Recently closed` is in the index only. Orientation reads the index plus its own inbox (Query Spec, sub-check (d)). An open action ask quiet for 21 days gets a one-line `<!-- quiet: N days -->` comment from the render; it is not a field, the parser skips it, and it never closes the ask (ruling R2). Design and reasons: DataWizard decision D165. (DataWizard, 2026-11)

**Recently closed, the archive and the targets list.** The index shows the 5 most recently closed rows. Terminal rows rotate to the monthly archive (the month of `updated`). The archive is append-only and keeps every version: an unchanged row is never archived twice, and a closed row that changes after it was archived (a resolution added, say) gets a new copy appended in the month of its new `updated`. Fold and rebuild take the copy with the newest `updated` (on a tie, the order in "The board files" above), so the archive alone can rebuild the newest state. The well-known targets - the store names and project session logs a pointer may name - live in `Board - Targets.md` beside the board. Edit that file by hand; the render writes a starter only when it is missing and never overwrites it. (DataWizard, 2026-11)

**Who writes the table.** Board table writes run on the operator's machine only - the board script, Claude Code sessions, and the DW Save sync, which runs the board render at every save. A session working through a mount that cannot forward SQLite locks (for example a Cowork session) never writes the table; it uses the hand path: write the block at the end of the index `## Live` in the board's grammar, re-read, renumber on collision (Optimistic-claim pattern); release or pick up by editing the row's `status` and `updated`. The next render folds hand edits in: a row in both the board files and the table takes the side with the newer `updated`, field by field (a tie goes to the table); a row only in the board files is inserted under its own number (a different row under that number is a collision, carried to `## Unreconciled`, never inserted); a table-only row is written to its board file; every merge is reported; nothing is deleted on either side. Starter file: `Seed/Templates/Coordination Board - Template.md`. A render rewrites the header of the index and of each inbox from the script's own copy. A closing session may add one optional `resolution:` line to an ask, saying how it closed; the render keeps it. (DataWizard, 2026-10)

**Claims for an operator step: post them just before the run.** A claim that covers a step the operator runs by hand (a script on the operator's machine) is posted when you hand over the command, not when the work is staged. A claim lasts its ttl (120 minutes by default), and a render sets a claim that outlived its ttl to `expired`. If the run slips past the ttl - an overnight pause is the usual case - post new `held` claims just before the run, and set each old block to `status: reclaimed` with `- reclaimed_by: <the new id>`. Release the new claims when the run is checked. In one run, two claims posted at staging expired overnight and were renewed the next morning. (DataWizard, 2026-10)

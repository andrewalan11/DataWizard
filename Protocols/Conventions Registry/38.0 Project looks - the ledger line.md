# 38.0 Project looks - the ledger line

**Rule:** a project's look at a subject is one line in the project's ledger, the Research Tracking Index, with the same columns and the same words in every project. The line owns the outcome word. A view note or Fit section holds the reasons and points at the line. One script writes lines. The looks table is a derived index and reports only. The index reads a `harvest_log` state only when the project has no ledger line for the link, as a work state with no outcome, and as the Roll-up does (YAML Schema 2.0). (D183, DataWizard 2026-11)

**Fields.** A look line has twelve fields, in this order: Subject (a readable name); Kind; Key (one or more, each marked strong or weak: a `core_id` and an exact repo key are strong, every other key is weak until the operator confirms it); Date (ISO date of the look); Depth; Relevance; For (the project the relevance is about, when it is not the ledger's own, as its abbreviation; the abbreviation's one owner is the Vault Config row `holon_lens_map`); Outcome (the one home of this fact); Trigger (for a queued look, what should cause the look); Finding (what was found, in the project's own words); View note (pointer to the project's view note or Fit section, if one exists); By (session id, and the model when a model wrote the line). A second look at the same subject is a new line. The newest line per project and subject is current; older lines are the history.

**Words.** Kind: `tool`, `org`, `link`, `work`, `place`, `question`. Depth: `listed` (saw the title or a listing only); `light` (read the landing page, the post, or the README summary); `moderate` (read the full piece or the docs; no source code read); `deep` (read the source code or the primary material in depth); `tested` (ran it); `not set` (no depth was recorded). Relevance: `high`, `medium`, `low`, `none`, `not set`, one shared scale for all projects; a project's own words stay in the Finding. Outcome: `queued` (not looked at yet; the project wants to); `adopt` (in use, or will be); `test` (the project plans a test); `watch` (not now; look again later); `applied` (something from it went into a design or a document); `confirms` (it supports what we already do; nothing changes); `reference` (kept as a source or an idea); `pass` (looked, not wanted); `duplicate` (the same subject as another line); `superseded` (a newer subject replaced this one); `unavailable` (the content could not be read). Not used as look words, because each already has another meaning: status, maturity, verdict, evaluated, used, try.

**Line grammar.** A look line is one row of a markdown table, with twelve cells in this order: `| Subject | Kind | Key | Date | Depth | Relevance | For | Outcome | Trigger | Finding | View note | By |`. Subject is free text. Kind is one word from the Kind list. Key holds one or more keys, separated by `; `. Each key is `scheme:value`, and the schemes are `core`, `repo`, `url`, `host` and `name`. `core` (a `core_id`) and `repo` (an exact repo key) are the strong keys; all other keys are weak. The writer puts the keys in the order `core`, `repo`, `url`, `host`, `name`, keeps the given order inside one scheme, and refuses the same key twice. A `core` value is the `core_id`; a `repo` value is the repo key in lower case, `github-repo~owner/repo` or `git-repo~host/owner/repo`, without a final `.git`. A `host` value is lower case, without `www.` and without a port; a `name` value is a slug (ASCII, lower case, text in brackets dropped, a leading "the " dropped, every other run of characters one `-`), and the writer refuses a value that is empty after this. A URL key is written `url:<normalised>`, followed by ` raw:<raw>` only when the raw URL is not `https://` plus the normalised form. To normalise a URL, lowercase the host, drop `www.`, drop a trailing `/`, and drop a leading `http://` or `https://`. A key value may not contain `; ` or ` raw:`, and the writer refuses such a key; a `;` followed by a space is written `%3B`, and a space in a URL is written `%20`. Date is `YYYY-MM-DD`. Depth, Relevance and Outcome each hold exactly one value from their lists; `not set` is two words but one value. For is empty, or one project abbreviation from the Vault Config row `holon_lens_map`; the writer refuses the ledger's own abbreviation, so leave For empty then. Trigger is free text; it is required when Outcome is `queued` and empty for every other Outcome. Finding is free text. View note is empty or one wikilink. By is the session id in the form the project's session-closer gives for an edit_log entry, without the date (a converted row with no session has the word `unlogged`), then optional parts separated by `; `, in this order: `model=<model>` when a model wrote the line, then one or more `from=` parts for a converted record, the file pointer first and the database pointer after it. `from=<file>#<n>` names a table row: `<file>` is the file name without `.md` and without a path, and `n` counts the data rows of every table in that file, from the top, starting at 1. `from=<file>#h<n>` names the n-th `### ` block in a file; `from=research_items#<id>` or `from=queued_items#<id>` names a database row. An empty cell has nothing between its pipes. A pipe inside a cell, also in a wikilink alias, is written `\|`, and there is no other escape. A cell holds no line break and no tab; the writer refuses one.

**Where lines go.** Lines go in one table per section note, under a `## Looks <year>` heading, and each such note carries the ledger flag `look_ledger: <ABBR>` (YAML Schema). A year may have more than one section note: `<n>.0 Looks <year> - <ABBR> Research Tracking Index.md`, then `<n>.1 Looks <year> - Part 2 - <ABBR> Research Tracking Index.md`, and so on. For a new year `<n>` is the next free whole number in the sections folder, and each later part takes the next free number in its group (`<n>.1`, `<n>.2`, and after `<n>.9` comes `<n>.10`). Each section note is embedded in the ledger shell as `![[<note name>]]` after a blank line: the first part of a year at the end of the shell, under a grow line, and a later part right below the embed of the part before it. A line goes in a section of the year of its Date; the writer refuses a line whose Date is in another year. The writer measures the note on disk before the append and refuses to add a line to a note of 40 KB or more (40 x 1024 bytes), and says to start the next part. It refuses to start a new part while the newest part of that year is under 40 KB.

**Line id.** A line has no id field. Its id is the first 10 hex digits, in lower case, of the sha256 of the UTF-8 bytes of the twelve cell values, each trimmed of spaces and unescaped (only `\|` becomes `|`), joined by a tab; an empty cell is the empty string. So a re-padded cell or a changed line ending does not change the id. The writer checks the note it writes and refuses a line whose id is already in that note. The look index reports an id that repeats across notes. (D183, DataWizard 2026-11)

**Frozen banner.** One line, right after the "Part of" line of each frozen old section: `*Frozen <YYYY-MM-DD> (D183): old rows kept as history; do not edit. New looks: [[<year section>]].*` A note is frozen when a line starts with `*Frozen ` and contains `(D183)`. A script writes the banner, never MCP. If the note has no 'Part of' line, the banner goes right after the frontmatter. The link names the first section note of the year. The frozen refusal applies to `add`; `init` may still add its embed line to a frozen shell.

**The `(D183)` token.** The text `(D183)` in the banner is a format token, not a citation. Scripts recognise a frozen note by a line that starts with `*Frozen ` and contains it, so write it exactly as shown, even if the decision is later renumbered or retired. This entry is its definition.

**The `holon_lens_map` row.** The Vault Config Paths row `holon_lens_map` is a list of `<folder>/=<ABBR>` entries separated by `; `. Each entry says that the notes under that vault-relative project folder belong to the project with that abbreviation (a capital letter, then up to nine capitals or digits), for example `_Alpha/=AL`. The row is the one owner of the abbreviation: the ledger flag `look_ledger: <ABBR>` (YAML Schema 1.0, Ledger Flag) and the For cell must name an abbreviation that is in it, and the line writer refuses one that is not. A project must add its row before its first look, and before the first run of the line writer's `init` (Seed Install and Update guide).

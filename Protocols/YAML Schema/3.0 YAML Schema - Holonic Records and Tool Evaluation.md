# 3.0 YAML Schema - Holonic Records and Tool Evaluation

### Holonic Records (`hid`, `entity_kind`, lifecycle, `relations:`, and the `core_*` cluster)

A *holonic record* (a *core*) is the one project-agnostic note for a thing several projects each describe from their own angle. The core holds the shared facts and a stable identity; each project keeps a *projection* - its own note, in its own folder, carrying a self-contained `## Shared facts (from core)` block plus the project's view. The vault is the authority for identity, lifecycle and relations; every database that reads cores is an index. Rule and sync contract: Conventions Registry, "Holonic records". Adopted as DataWizard D133 and D134 (2026-10).

**On the core note** (`type: entity`, in the owning vault's `_Entities/` folder):

```yaml
type: entity
entity_kind: org            # one value from the kinds table below
hid: k7m2p4q3r3t5w6x2y6z4   # 20 chars a-z 2-7, minted once by the index, never derived from a name
core_id: example-org        # kebab-case, stable forever once written; the human key
name: Example Org
aliases: []                 # real other names only (acronym, aka, former name) - never a parent
website: https://example.org/   # the entity's own site, never a shared host
keys: []                    # asserted lookup keys as <scheme>~<value> (anchor table below)
one_liner: ...
status: active              # active | merged | retired
# successor: <hid>          # only when merged
# merged_from: [<hid>]      # only when this core absorbed another
relations: []               # list of relation records (shape below)
to_confirm: []              # facts not verified at the source, with where they came from
projections: []             # one entry per place the entity appears, with a state (below)
sources: []
verified: YYYY-MM-DD        # last check against the entity's own site, or `unverified`
```

Kind-specific shared facts (`org_form`, `founded`, `location`) follow the kinds table. `unknown` is a legal value in the core (checked, not found); the projection block omits a bullet whose value is unknown.

**Kinds** (the only place a kind is defined; consumers import this table, never the reverse):

| Kind | What it is | Extra shared facts |
|---|---|---|
| `org` | an organization of any legal form | `org_form`, `founded`, `location` |
| `network` | an association of orgs or people with its own name | `org_form`, `founded`, `location` |
| `fund` | a pool of money with a name and a steward | `org_form`, `founded`, `location` |
| `community` | a place- or practice-based group without a formal body | `founded`, `location` |
| `platform` | software people use as a service | `org_form`, `founded` |
| `protocol` | a specification several implementations follow | `founded` |
| `tool` | software people install or run | `founded` |
| `person` | a human being - see the person rules below | none |
| `project` | a bounded effort with a name, including the vault's own projects | `founded`, `location` |
| `place` | a venue, region or site | `location` |
| `event` | a dated gathering | `founded` (the date), `location` |
| `work` | a text, talk, recording, film or dataset | `founded` (publication date) |

A kind is added when a real record of it is touched, by adding a row here and a Seed patch note. `entity_kind` on a note that is not a core is ignored by the index.

**Identity.** `hid` is the join key for every index and every consumer; `core_id`, slugs and hosts are lookups. The index mints `hid` on a core that lacks one and writes nothing else back. `keys:` holds asserted lookup keys as `<scheme>~<value>`; derived keys (`core~`, `host~`, `slug~`) are computed by the index and never stored. Normalisation: lowercase; no protocol, `www.`, port, query or trailing slash; non-ASCII hosts to punycode; a value that normalises to empty is not a key. A key is retired by moving it to `keys_retired:`, never deleted.

| Scheme | Value | Example |
|---|---|---|
| `linkedin` | path after the host | `linkedin~in/jane-example` |
| `github` | login | `github~example-org` |
| `github-repo` | one repository: owner/repo, lower-cased (the login alone is `github`) | `github-repo~example-org/example-tool` |
| `npub` | bech32 Nostr key | `npub~npub1...` |
| `did` | the DID | `did~did:web:example.org` |
| `purl` | Murmurations primary_url, host form | `purl~example.org` |
| `profile:<host>` | path on that host; covers any host not listed | `profile:example.social~jane` |

Scheme rows are added as a project needs them; `profile:<host>` is always available.

**Stored form of a key.** The table shows what a core's `keys:` holds: the plain `<scheme>~<value>`. The index does not always store a key that way. Its key function keeps the plain form only when the whole `<scheme>~<value>` string uses the key alphabet (letters, digits and `_ - . ~ : @ +`) and is at most 200 bytes. Any other key (a "/" in the value is enough) is stored as `<scheme>~sha256-<hex>`, where `<hex>` is the SHA-256 of the normalised value (UTF-8). A `github-repo` value always has a "/" (so does a `linkedin` value), and `purl` and `did` keys are always hashed, so the operational database holds `github-repo~sha256-<hex>`, never `github-repo~example-org/example-tool`. A consumer that joins a core to the index hashes the plain key from the core's `keys:` with the index's own key function (for `github-repo` it lower-cases the value first and checks that it is `owner/repo`), and checks the result against that holon's active keys (a retired or held key does not count). Never compare plain text with the database, and never strip the scheme prefix and compare the rest: neither can match. Import the index's function instead of writing a second copy, so one file owns the rule. (DataWizard, 2026-10)

**Lifecycle.** `status: active | merged | retired`. A merge or retirement is an operator ruling recorded in the core's `edit_log` and the Decision Log; scripts never set these values. Merged: the loser carries `successor` and `merged: YYYY-MM-DD`; the survivor carries `merged_from`, gains the loser's aliases and keys, and the loser's projections are re-pointed at the survivor on the next sync (the one authorised re-key of a projection). Retired: `retired: YYYY-MM-DD`. Nothing is deleted; a chain of successors is reported, not followed.

**Relations.** `relations:` is a list of records. A relation lives on the core of its subject; the declared direction is the only one stored; inverses are derived. On a core a relation is a shared fact; on a projection it is that project's view.

```yaml
relations:
  - pred: part_of           # from the predicate table
    target: m4k7q2w3x3z6b5c5d2f4   # target hid; a core_id is accepted and rewritten to the hid on the next federating write; null when no core exists yet
    target_name: Example Network
    role: hub               # optional qualifier; the source verb for related_to
    since: 2021             # optional, YYYY or YYYY-MM-DD
    source: _Projects/Example Org.md#relations[0]   # vault locator, register locator (<project>:<row>.<field>) or URL
    raw: 'part-of: Example Network'                 # optional, the source string verbatim
```

The trailing `# ...` comments in this example and the core example above explain the fields; they are not canonical YAML. A stored record carries no inline comments, and a reader never has to strip them.

A relation is created and retracted, never edited in place: a correction is a retraction (`retracted: YYYY-MM-DD`, `retracted_by`, optional `retracted_reason`) plus a new record, and the retracted record stays. A relation has no stored id; its identity is `(subject hid, pred, target, role, since)`. Records keep their place in the list: a retracted record stays at its index, a replacement is added at the end, and no record is ever removed, spliced or re-ordered, because a consumer may derive an id from a record's position (Holonic Canvas, 2026-10).

| Predicate | Inverse (derived) | Symmetric | On a core |
|---|---|---|---|
| `part_of` | `has_part` | no | yes |
| `member_of` | `has_member` | no | yes |
| `home` | `home_of` | no | at most one |
| `works_for` | `employs` | no | yes |
| `founded` | `founded_by` | no | yes |
| `leads` | `led_by` | no | yes |
| `builds` | `built_by` | no | yes |
| `partner_of` | - | yes | yes |
| `funded_by` | `funds` | no | yes |
| `builds_on` | `built_on_by` | no | yes |
| `uses` | `used_by` | no | yes |
| `federates_with` | - | yes | yes |
| `same_as` | - | yes | by a merge only |
| `authored_by` | `author_of` | no | yes |
| `cites` | `cited_by` | no | yes |
| `quotes` | `quoted_by` | no | yes |
| `depicts` | `depicted_in` | no | yes |
| `derived_from` | `source_of` | no | yes |
| `related_to` | - | yes | with `role` only |
| `affiliated_with` | - | yes | view only |
| `knows` | - | yes | view only |
| `best_connection_to` | - | no | view only |
| `represents` | `represented_by` | no | view only |

Adding a predicate is a schema change. Role words that have a finer predicate map to it (`founder` -> `founded`, `builder` -> `builds`, `leader` -> `leads`, `member` -> `member_of`; `user`, `runs on`, `hosted on`, `publishes to` -> `uses`); other role words stay as `role` on `part_of`. A verb with no predicate becomes `related_to` with the verb in `role`. `uses` points from the user to the tool (an org, project or community runs it, hosts its community on it, or publishes through it); `builds_on` stays the dependency of one product on another.

**Provenance (`by`, `via`).** Optional on a `relations:` record and on a `field_sources` entry (where a project's records carry per-field sources). `by` is the person the change was made for, as `member:<key>` - never an agent or a tool. `via` is the custody path, an append-only list of hops oldest first, each `<kind>:<id>` (for an agent hop, `agent:<project>/<session>`); a hop carries no time. The hop-kind list is open; the Registry's table is the lint set. `source` keeps its meaning (where the fact came from); `by` and `via` say who the change was for and how it travelled. Rule, hop kinds and example: Conventions Registry, "Provenance: by and via".

**Persons.** A person core (`entity_kind: person`) exists before anyone claims it; consent governs exposure, not existence. Fields beyond the common set: `person_state: unclaimed | anchored | claimed` and `exposure: team | public` (default `team`). Allow-list: `hid`, `core_id`, `name`, `aliases`, `website`, `keys`, `keys_retired`, `person_state`, `exposure`, `one_liner` (from the person's own public profile only), `relations` (each with a public `source`), the `status` cluster, `to_confirm`, `projections`, `sources`, `verified`, birth metadata. Any other field is an error. Relationship content about a person never enters a core at any state; it stays in the project's own notes. `unclaimed -> anchored` when the operator adds the first key; `anchored -> claimed` through a claim flow defined outside this schema (first implementation: the ontology doc "Fact Tiers, Persons and Personas" in the Holonic Canvas project - the three states and the persona artifact; Holonic Canvas, 2026-10); `public` exposure is reachable only from `claimed`.

**`projections:`** entries are `<path or place> (<state>)`; states: `written YYYY-MM-DD`, `existing note - shared block added YYYY-MM-DD`, `pending pickup - exchange note`, `pending pickup - handoff file`, `existing collaborator note, not edited - <project>`, `list entry, not a note`, `registry row, not a note`, `queue line N, graduated YYYY-MM-DD`, `retired YYYY-MM-DD`, `merged into <core_id> YYYY-MM-DD`, `merged from <core_id> YYYY-MM-DD` (never removed).

**On every projection** (a project's own note about the entity):

```yaml
core_id: example-org
hid: k7m2p4q3r3t5w6x2y6z4
core_note: _Entities/Example Org.md    # plain path, never a wikilink
core_synced: YYYY-MM-DD
```

`hid` is the join; `core_id` and `core_note` tell a human where the core lives on the far side of a vault boundary. `core_note` is the one deliberate exception to "Wikilinks everywhere" (top of this document; Conventions Registry, "Self-contained boundary-crossing references"). `core_*` fields and `hid` are written only by the federating skill, its batch twin, or the index - never by hand-maintained project views. These fields are unrelated to the Federation Fields above (`federated_to` / `federated_from` copy a file; a core record is a join, not a copy).

### Tool Evaluation Notes (`verdict`, `fit`, `safety` and the evaluation fields)

A *tool note* is the one shared evaluation of a tech tool (a code repo, an app, a model or a service) in the vault's tool-evaluation project. Rule (three notes per tool, look there first, who writes, when a tool gets a core, naming): Conventions Registry, "Tech tool evaluations". A tool note is `type: resource`. Before the tool has a core it carries no holonic fields; after that it is a projection and gains the four projection fields above.

```yaml
repo_key: example-org/example-tool   # repos only: lower-cased owner/repo; the value of the core's github-repo key
source_url: https://example.org/tool   # tool notes born from an intake link: that link, as saved
one_liner: ...
license: MIT                 # SPDX id; `none found`; `<id> (README only)` when only the README states it
mac: yes                     # one field per operator platform (here `mac`): yes | partly | no | unclear
tool_maturity: active        # the tool's state: active | alpha | frozen | archived | unknown
categories: [video-editing]  # kebab-case slugs; `other` when none fits
reviewed_by: [Project A]     # projects that evaluated the tool (who looked), by name
fit: [Project A]             # projects the tool fits, by name; the reasoning stays in each project's note
verdict: ""                  # the operator's answer only: clone | later | skip | cloned; empty = not decided
safety: not checked          # one safety word (below)
safety_checked: YYYY-MM-DD   # date of the check that set `safety`; empty while `not checked`
safety_by: agent:<project>/<session>   # who or what checked: one hop in the via hop form
```

The trailing comments explain the fields; they are not canonical YAML (as in the Holonic Records examples).

- **Platform field:** each operator keeps one field per platform the tool must run on, named for the platform (for example `mac`), with the same four values.
- **`tool_maturity`** is the tool's state. It is distinct from the document `maturity` field (Document Weighting), which tool notes do not use for this. A tool core's `maturity` is the CS-scale field of Holonic Records, a different scale.
- **`source_url`** links a tool note born from intake to its intake item, so a script finds the item without parsing `origin:`. Write the link as it was saved; intake scripts normalize it when they match. The session that creates the note from an intake item writes it. Notes not born from intake leave it out.
- **`verdict`:** `clone`, `later` and `skip` answer a review of a repo not yet on disk; `cloned` marks a repo that is already on disk. Like the other values, `cloned` is the operator's own answer; no script sets it (a scanner's own keys already record that a repo is on disk).
- **`safety`** takes only these words: `not checked` | `look-first (<reasons>)` | `no concerns found (<tier>, <tools>, <date>)` | `do not clone (<reason>)` | `human-audited`. Never "safe" or "clean". `no concerns found` promises only that no repo code ran, that the named files were read, and that cloning and reading the code is fine. It says nothing about installing dependencies or running the tool.
- **`safety_by`** names the checker as one hop in the `via` hop form of "Provenance: by and via" (Conventions Registry): `agent:<project>/<session>`, `task:<name>`, or `member:<key>` for a person's audit.
- **Who writes:**
  - A repo scanner's note writer owns its own keys (`repo_key` and its catalog keys) and its marker blocks. For a repo not yet cloned, the review that creates the note writes `repo_key`.
  - Sessions write the evaluation fields and the hand region.
  - The operator sets `verdict`.
  - A safety or usefulness review writes the `safety*` fields and proposes `fit` names.

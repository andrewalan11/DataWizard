# 4.0 web_fetch Behaviors

**Token-cap overflow saves to a temp file.** When a page exceeds the token cap, `web_fetch` errors and saves the content to a temp file. In practice, search-result summaries plus one canonical readable page were decision-grade -- budget for this rather than retrying the same oversized fetch. (Source: RW S23)

- Cowork WebFetch can refuse arbitrary URLs with PROVENANCE_REQUIRED: a permission prompt goes to the human and, unanswered, the fetch fails - fatal for unattended runs. Workaround that held everywhere tested (Weave, 2026-09): run a web search naming the target first, then fetch the URLs the search returns - search-derived URLs carry provenance. Design scheduled web checks search-first, and report still-blocked sources as unverified rather than retrying.
- The provenance gate is not universal: in an attended Cowork session WebFetch fetched an arbitrary Firebase-hosted page directly with no prompt (Weave, 2026-09). Plan search-first for unattended runs; do not assume the gate in attended ones. Separately, WebFetch sees only server-rendered HTML - a JS-rendered page returned just its toolbar and snapshot stamp; use Chrome MCP (see Reading Client-Rendered Pages) for the content.
- When the gate does fire in an attended session, the approval prompt can time out unanswered and the fetch fails the same way. The reliable unblock is to ask the operator to paste the URL into the chat - a pasted URL carries provenance. Do not loop on the fetch while the prompt is pending. (DataWizard, 2026-09)

- A `claude.ai/share/<id>` conversation link is not readable by `web_fetch` - it returns only the site's meta tags, never the shared chat. Ask the operator for the underlying vault note or artifact instead; a `claude.ai/artifact/<id>` link IS readable, through the Artifact tool's read action (not web_fetch), and a large artifact comes back head-only with the full HTML saved to a local file. (DataWizard, 2026-10)
- Reddit is blocked at the WebFetch proxy: `reddit.com` returns 403 / SITE_BLOCKED, re-confirmed across sessions. Read a thread through the browser tools (`get_page_text`), from a saved copy in the vault, or from an operator paste; do not script around the block. WebSearch cannot reach Reddit either. Reachability differs by surface: the device shell on the operator's Mac resolves a Reddit `/s/` share link to the post slug and og:title (`curl -A facebookexternalhit`), while Reddit's JSON endpoints return nothing. (VibeCut, 2026-08/09; DataWizard, 2026-10) Share links, `old.reddit.com` and `.json` URLs were blocked the same way through WebFetch, and the Claude-in-Chrome extension refuses reddit.com and old.reddit.com (10.0). For an intake item that is only an image or video with no repository link, ask the operator to read the post: one sub-agent web search found 2 of 6. (Tech Tools, 2026-10)
- WebFetch can return a cached page for the wrong URL. Two different Hacker News item ids, one of them also tried with a query-string variant, came back with identical content; the collision cleared on a delayed retry days later. When fetches of different URLs return the same content, treat it as a transient cache collision and retry once after a delay before declaring the content unreachable. (VibeCut, 2026-08)
- WebFetch on GitHub reads open items but not history. A single open pull request (`/pull/<n>`) and the open-PR list read fine; the closed-PR list, a PR search by author and the commit log return `ROBOTS_DISALLOWED` (a project's own build-artifact host refused the same way). So "no merged PR seen" from WebFetch is not evidence that none was merged: report the history as unreadable, and read it with the browser tools or a user-run `gh` command (`gh pr list --repo <owner>/<repo> --state all --author <login>`; `gh api repos/<owner>/<repo>/commits`). Search pages (`github.com/search`) answer `ROBOTS_DISALLOWED` too, and one session had a pull list refused (the record does not say which list), so do not count on any list page. Fetch the org or repo URL directly. For licence text, read the raw file: `raw.githubusercontent.com/<owner>/<repo>/HEAD/LICENSE`, or `LICENSE.md`. Tree and commit pages: Cowork Build Environment, Network and GitHub Data. (Weave, 2026-10; Community Stack, 2026-10; DataWizard, 2026-10)
- WebFetch and gitlab.com: the GitLab REST API (`gitlab.com/api/v4/projects/...`) answered `ROBOTS_DISALLOWED`. A gitlab.com project page was blocked for research sub-agents in one session, yet the same page read fine (creation date, commit count, licence) from another session the same day. In the blocked run the GitHub API and the Docker Hub v2 tags API (`hub.docker.com/v2/...`) were readable. For a GitLab-hosted project, read the project page directly and do not count on the API. When a sub-agent reports the page blocked, have the lead try it once, later (a quick retry of a just-failed URL is refused - next bullet), before you take dates and counts from search results; then say which facts came from search. A self-hosted GitLab behind a bot-check wall: section 10.0. (DataWizard, 2026-10)
- WebFetch can refuse a second fetch of a URL that failed a few minutes earlier in the same session. The refusal reads like "failed 251s ago ... a second fetch this soon nearly always fails". It also hits the lead after a sub-agent's failure. Do not retry the URL at once. Use another path (the browser tools, a raw file URL) or try again much later. (Community Stack, 2026-10)
- WebFetch can serve an old snapshot of a GitHub repo page. For four repos, `github.com/<owner>/<repo>` came back with old star counts, commit counts and descriptions. One page showed 0 stars and 13 commits where its raw README and the commits API showed about 248 commits and a longer item list; two others showed fewer stars than the search API did. The page reads normally, so nothing marks it as old. For counts and current state, read raw files (`raw.githubusercontent.com/<owner>/<repo>/HEAD/<path>`) and the API (`api.github.com/search/repositories?q=repo:<owner>/<repo>`, `/commits`, `/releases/latest`). Report repo-page numbers as "reported, may be stale". A third-party page about a repository can lag the same way: a news page showed an older "last updated" date and an older feature list than the repository. Check the project's own changelog or release page, not the news page's date, before using it to correct a claim. (Future Visions, 2026-10)
- `api.github.com/repos/<owner>/<repo>` can be blocked or stale for a sub-agent while the other GitHub API routes answer. For some worker-tier sub-agents it was refused; one got old numbers from it (a date before a known rename). In the same runs the `/commits`, `/releases/latest` and search routes worked, and `/commits?per_page=1&page=<n>` (n = the commit count) gave the first commit date. Do not take current state from `/repos/...`; use the routes above. Other GitHub API refusals: Cowork Build Environment, Network and GitHub Data. (Future Visions, 2026-10)
- Kickstarter project pages (`kickstarter.com/projects/<creator>/<project>`) are not readable by the web tools. WebFetch returned only header data (title, amount pledged, backer count) and none of the story, reward tiers, risks, FAQ or updates, and `curl` from the cloud container got HTTP 403. Two research sub-agents hit this independently. Treat the missing sections as unread, not as absent (the same title-only shape as Reading Client-Rendered Pages, rung 9). The headline numbers came from a tracker site (Kicktraq) and the creator's own newsletter posts; the reward tiers need a browser pass in Chrome. (Rootland, 2026-10)
- **LinkedIn short links (`lnkd.in/...`) fail in WebFetch (robots disallowed); the operator's signed-in Chrome opens them.** Open the link with the Claude-in-Chrome tools and read the post with `get_page_text`. The first `get_page_text` right after `navigate` can fail with "page navigated to a different domain" while the redirect finishes; call it again. (ReWoven, 2026-10)
- **Pinterest boards: WebFetch refuses pinterest.com (`robots_disallowed`) - do not script around it; read what the operator shows.** The operator opens the board in their own Chrome and scrolls it; the agent reads the screenshots (zoomed out, a board of 17-24 pins fits in two or three frames). Pin `alt` text is generic ("This may contain: ..."), so read the screenshots, not the alt text. (Kosmosis, 2026-10)
- **Reddit in the operator's logged-in Chrome: `/api/morechildren` answers 403 (since 2026-10), while post JSON and continue-thread JSON still answer 200.** A console capture snippet should skip the load-more calls and mark the capture as truncated instead of failing. (DataWizard, 2026-10)
- **Google Maps short links (`maps.app.goo.gl/...`): WebFetch answered `RATE_LIMIT_EXCEEDED` twice in a row; resolve them in the device shell.** `curl -sI <short link>` returns the 302 with the full `google.com/maps/place/...` URL in `location:`, and its `!3d<lat>!4d<lon>` part is the exact pin. No browser needed. One link at a time, not a bulk resolver; if `curl` is rate-limited too, stop. (LocationScout, 2026-10)
- **WebFetch returns a model's reading of the page, so a "quote" from it can be a paraphrase.** In one listings sweep a helper marked its quotes "(paraphrase)", and a reviewer still found one invented quote in the data. Ask for the text verbatim (Reading Client-Rendered Pages, rung 4), label a quote that was not read verbatim as a paraphrase, and spot-check a sample against the source before a page ships. (LocationScout, 2026-10)
- **Property and rental portals (Germany, Austria): reachability in one sweep by research sub-agents.** ImmoScout24.de returned errors to WebFetch while ImmoScout24.at mostly fetched fine (`.de` search: operator-led reading, rung 13); its card price is the cold rent, the warm rent is on the detail page. On immowelt the `classified-search` URLs are robots-disallowed (leave them to operator-led reading); the `/liste/<town-or-district>/wohnungen|haeuser/mieten` lists are allowed and fetched - page 1 only (about 30 cards; pagination is ignored). Blocked or empty: willhaben.at, immo.sueddeutsche.de and ovb-online.de (SITE_BLOCKED; respect the block - an aggregator that lists the same ads with its own permission is a separate source, not a way into the blocked site), derstandard.at property (privacy wall), homelike.com (robots), Wunderflats search, meinestadt.de. wg-gesucht URLs need a numeric city id, and a wrong id silently returns another city. On Airbnb the filter panel had no bathtub amenity in one run (another run had one; locale or A/B test), and a guessed amenity id in the URL was a different amenity: read features from each listing's full amenity list, never from a guessed filter id. (LocationScout, 2026-10)

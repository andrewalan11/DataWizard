# 11.0 Claude Code Cloud Sessions

Behaviors of Claude Code sessions that run in Anthropic's cloud (started from claude.ai/code, the desktop app's Code tab with Cloud, `claude --cloud` or the mobile app), as distinct from a Cowork session with a linked computer. Several of these rest on a product setting or promotion that can change: read the live source before you plan around one.

- **A promotional credit for cloud sessions did not cover Cowork tasks.** The promotion's support article lists claude.ai/code, the desktop Code tab with Cloud, `claude --cloud` and mobile as covered. A plan that put Cowork scheduled tasks on the credit was wrong; work meant for the credit has to start from one of the listed surfaces. This is a snapshot of one promotion (Conventions Registry, "Carry the probe, not the snapshot"): read the live article before you rely on it. (DataWizard, 2026-10)
- **A cloud session reaches a private repository only when the Claude GitHub App is installed on it.** An app that is listed under "Authorized GitHub Apps" for the account is not enough. Install it at github.com/apps/claude, then Configure, then choose selected repositories, and pick only the repository the session needs rather than "all repositories" when other repositories on the same account should stay out of reach. (DataWizard, 2026-10)
- **A cloud session cannot create a repository.** `gh repo create` from the session answered with a proxy 403. The operator creates the repository and installs the app on it; the sessions then push their work to their own branches. (DataWizard, 2026-10)
- **The environment's "Limited" network takes one domain per line, and the safety scanners need four hosts beyond the defaults.** `objects.githubusercontent.com` and `release-assets.githubusercontent.com` (release downloads redirect there), `api.osv.dev` and `osv-vulnerabilities.storage.googleapis.com` (OSV-Scanner's advisory data). OSV-Scanner errored until `api.osv.dev` was allowed. A test run on one repository found this before a 28-repository batch. (DataWizard, 2026-10)
- **GuardDog installed only through pipx there.** Use `pipx install guarddog==<pinned version>`; see [[10.0 Scanning Third-Party Code]] for the scanner's own behaviors. (DataWizard, 2026-10)
- **A cloud session can clone a public repository that is not attached to it.** A test clone of an unattached public repository passed. (DataWizard, 2026-10)
- **A cloud clone can be shallow (depth 1), and then every git command that names an older commit id fails.** `git diff <old-sha>`, `git show <old-sha>:file` and `git log --diff-filter=AM` exit 128 ("Not a valid object name") or show only the tip. The repo-attach step (`add_repo`) in a Cowork session clones with `--depth 1`, and a review of a build run card found this as a blocker. Fix that was tested, in the run's first phase: `git fetch --unshallow origin`; if that is refused, a bounded `git fetch --depth=1000 origin main`; if old ids still do not resolve, skip only the history-based checks and keep the file-hash checks. In a committed test, pin a file by its sha256, not by `git diff <old-sha>`. A probe on a full clone does not find this: test on the clone shape the run will get. Pushing a new branch from a shallow clone worked. (Kosmosis, 2026-10)
- **Fetching a non-default branch into a depth-1 clone needs explicit refspecs.** `git fetch --depth=50 origin main <branch>` only fills `FETCH_HEAD`; `origin/<branch>` does not exist afterwards, because a depth-1 `git clone` tracks only the default branch. Give the refspecs: `git fetch --depth=50 origin +main:refs/remotes/origin/main +<branch>:refs/remotes/origin/<branch>`. Then `git merge-base` shows at once whether `main` can fast-forward. (Kosmosis, 2026-10)
- **In a cloud session `gh` can be installed but not logged in.** `gh` was at `/usr/local/bin/gh`, but `gh auth status` exited 1 with "The token in GH_TOKEN is invalid", so `gh pr create` could not run, even with the Claude GitHub App installed on the repository and `git push` to a branch working. One run first wrote "gh not installed" because it tested with `command -v gh`; test with `gh auth status`. For run cards: make a draft pull request optional, and plan for the operator to merge on the Mac (a fast-forward was enough for a solo project). (Kosmosis, 2026-10)
- **A repo agent type cuts a sub-agent's start-up text and enforces its tool list.** A general sub-agent carried about 76,000 to 83,000 tokens of start-up text (tools, instructions, repo notes). An agent type defined in the repo (`.claude/agents/<name>.md` with a `model:` line and `tools: Read`) cut that to about 15,000 to 36,000 and allowed only the one tool. A prompt rule alone did not stop a small-tier model from calling other tools: about 20 tries in one run, some to start sessions or suggest tasks. With the agent type there were none in two later runs. The strongest tier obeyed the prompt rule every time, so the agent type matters most for the small tiers. For any swarm of sub-agents, define a small agent type (or call the API directly with a short cached prompt) and do not use the default sub-agent. (DataWizard, 2026-10)
- **Attaching a whole private repository with `add_repo` can be refused by the session's permission check; stage the files the task needs instead.** Attaching the private repository that holds a whole vault was refused. Staging the needed files worked. Ask for the small repository set up for the job (with the Claude GitHub App installed on it, above), not the one that holds everything. (DataWizard, 2026-10)
- **`gh api` is blocked for sub-agents in a cloud session, and WebFetch cannot read GitHub commit pages.** Sub-agents that ran `gh api repos/<owner>/<repo>/commits` got 403 (the session is bound to its own repositories), and WebFetch of github.com commit pages is refused by robots.txt. GitHub org and repo HTML pages still give "last updated" dates, archive status and licence names. For commit-level dates, attach the repository with `add_repo`, or run `gh api` on the Mac. (Community Stack, 2026-10)

# 8.3 Device Bridge - Outages and Recovery

*Outage bullets that stay where they are: the session-disk and no-shell bullets and the bridge-drop bullet in [[8.0 Device Bridge]]; the bridge-drop bullet, with its hours-long case, in [[8.1 Device Bridge - Staging, Commits and Transport]]; Bridge Drops and Hangs in [[MCP Reliability and Write Verification]].*

- **An outage where every `remote-devices` call returns 503 "Service Unavailable" is neither the full-disk fault nor a bridge drop.** The tools stay in the tool list, but each call (`device_bash`, `device_list_dir`, `device_stage_files`, `device_commit_files`) answers 503, and so do other connectors; `get_device_info` may still answer. Tell the three faults apart by what still works. In the disk-full fault (session-disk bullet in [[8.0 Device Bridge]]) only `device_bash` fails; list, stage, commit and the MCP tools still work. In a bridge drop the tools leave the tool list or answer "not connected to the bridge". In this outage every call fails with 503. You cannot run `df` during the outage. After it ended, `df -h /sessions; df -i /sessions` read about 1% used, which shows it was not the disk, so a session-disk swap is not the fix. It cleared on its own after about five hours (seen once). While it lasts, keep building in the container, let sub-agents save their output there, and commit after the bridge returns, as in the bridge-drop bullet in [[8.1 Device Bridge - Staging, Commits and Transport]]. One caution: the output folder a sub-agent saves to (`/mnt/user-data/outputs/`) may not be the lead's, so the lead checks that each file exists and compares its hash before the commit. This is the delegated-verdict rule: see Working Principles - continued, "A delegated agent's verdict is a claim until the lead reads the line". (DataWizard, 2026-11)

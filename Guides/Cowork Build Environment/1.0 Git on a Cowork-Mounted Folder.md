# 1.0 Git on a Cowork-Mounted Folder

The MCP Reliability guide documents the underlying restriction (the sandbox can create but not unlink files on the mount, so working-tree git ops orphan lock files). Build-workflow consequences:

- **Clear locks after every commit batch.** Commits can succeed while leaving stale `.git/index.lock`, `HEAD.lock`, `objects/maintenance.lock` and tmp object files that `rm` refuses ("Operation not permitted"). Clear them through the delete grant (`device_request_delete_permission`, then `rm`) or, with no grant, rename the empty locks aside directly under `.git` (never under `.git/refs`) once no git process is running - Git Guide 9.0 Troubleshooting and the MCP Reliability guide carry the recovery. Then verify with `git fsck`. Make this routine, not incident response. (Source: VC S27-S33, 6 recurrences; Holonic Canvas, 2026-10)
- **No git through the device shell on vault-mounted repos (Ruling R6, DataWizard, 2026-10).** Git runs in the operator's Terminal. One narrow exception: the lead seat may run git through `device_bash` when the delete grant is verified active in the same call sequence (with the grant on, `git am` / `git commit` leave `.git` clean). Never from a sub-agent - the grant is not inherited, and the sub-agent seat leaves `HEAD.lock` / `maintenance.lock` behind - and never unattended, since the grant lapses across a pause or reconnect. Lock-rename recovery (Git Guide 9.0) stays the fallback. (DataWizard, 2026-10; Holonic Canvas, 2026-10)
- **The device shell cannot run git inside a linked worktree.** A linked worktree (made with `git worktree add`) has a one-line `.git` file, `gitdir: /Users/<name>/.../<repo>/.git/worktrees/<name>`, and that Mac path does not exist inside the device shell's Linux VM, so even read-only `git diff` and `git log` there fail. Do not try to work around it from the device shell: the rule above stands. To have a worktree build reviewed from the cloud side, the operator runs `git diff`, `git log` and `git status` on the Mac and writes their output into a review-bundle folder (for example `git diff main...<branch> > <bundle>/04-diff.txt`), and the session reads the bundle and the worktree's plain files. (Rootland, 2026-10)
- **Read-only recon from the device shell can read git state as files.** For the branch and recent commits without `git status` or `git diff` (which can leave `.git/index.lock`, below), read `.git/HEAD`, `.git/refs/heads/*` and `.git/packed-refs` directly. A linked worktree's state is readable the same way through the primary checkout: `.git/worktrees/<name>/HEAD`, and during a rebase `.git/worktrees/<name>/rebase-merge/` (`head-name`, `onto`, `msgnum`, `end`, `done`) and `.git/worktrees/<name>/REBASE_HEAD`. `git worktree list` shows each worktree's real HEAD; run it on the Mac (rule above). Held across several read-only sub-agents with no lock left behind. (VibeCut, Rootland, 2026-10)
- **Read-only git can leave `.git/index.lock` too.** `git status` and `git diff` refresh the index and take `.git/index.lock` to do it, and through the device bridge the shell cannot remove the lock afterwards (field cases in the MCP Reliability guide, 12.0) - one more reason for the rule above. On the Mac, run read-only commands with optional locks off, for example `GIT_OPTIONAL_LOCKS=0 git status`, so they skip the optional index refresh and take no lock. (DataWizard, 2026-09)
- **A `git am` without the delete grant stops halfway** (first patch committed, the next stopped on `HEAD.lock`, with more lock files and `.git/rebase-apply` left behind). Recovery and prevention - request the grant before any git write on the Mac shell - are in Git Guide [[9.0 Troubleshooting]]. (Holonic Canvas, 2026-10)
- **The sandbox has no GitHub credentials and can never `git push`.** Pushes must run on the user's machine. A session log claiming commits were "pushed" is only trustworthy if the push actually ran there -- verify with `git status -sb` (ahead/behind), never assume. One session found three commits marked "pushed" that had never reached origin. (Source: VC S31)
- **`git commit -am` only stages modified tracked files** -- new files stay untracked and silently uncommitted. Use `git add -A`. One first-try commit left a whole session's new files behind. (Source: VC S34)
- **Cloning into a Dropbox-synced folder fails** ("unable to unlink .git/config.lock") because Dropbox locks files mid-sync. Clone to `/tmp` first, then `cp -R` into place. (Source: VC S24)
- **Git run on a Dropbox folder reached through the device bridge orphans `config.lock`.** A `git clone` or remote operation run with `device_bash` on a connected Dropbox folder left a `.git/config.lock` the shell could not unlink (the mount refuses deletes), breaking the operation midway. Recovery that worked: grant deletion on that folder (`device_request_delete_permission`), `rm -rf` the partial clone, and re-clone with `device_bash` - the device shell had network in that configuration. This covers external clones outside the vault; vault-mounted repos stay under Ruling R6 above. (VibeCut, 2026-08/09)
- **Git on a folder whose files Dropbox or iCloud has not downloaded fails with "Resource deadlock avoided" or a bus error.** From `device_bash`, `git` on a clone whose `.git` was online-only stopped with `couldn't read .git/packed-refs: Resource deadlock avoided` (or a Bus error), and `git status` printed a read error for each file. A code folder under `~/Documents` did the same, probably because of iCloud's Desktop and Documents optimization. No `index.lock` was left behind. A repository scan script reported its sync check as "not-checked" and the scan as partial. Fixes: in Finder choose "Make available offline" for the folder and wait, or have the operator run the git step (or the tar snapshot) in the Mac Terminal. (VibeCut, 2026-10)
- **A clone built with `git archive` has no history.** Crossing a tracked tree to the container as `git archive | gzip` plus `git init` is cheap and tests run, but anything that needs history or tracked-but-ignored files fails there (a `git rm --cached` of files the archive never carried). Keep history-dependent steps on the Mac and return commits as `git format-patch` files applied with `git am` (author and dates kept). An unattended session cannot land them: it hands off a format-patch tar plus `SHA256SUMS.txt` and the landing command. A `git bundle` is useless across a `git archive` base - its prerequisite commit (the archive's synthetic base) does not exist on the Mac. The same gap hits gitignored inputs: a test that reads a gitignored folder (for example a dated build or dry-run output) fails in the container until that folder is crossed separately as its own tar. Keep a list of the gitignored inputs the suites read beside the crossing command. (Holonic Canvas, 2026-10)
- **Crosses into a synced folder (Dropbox, iCloud) can leave `<name> 2.<ext>` duplicates** - one repo held 3,881 such files plus 26 `<dir> 2` folders. Safe sweep: delete an `X 2.ext` only when `X.ext` exists beside it and the hashes are equal, then remove empty `* 2` folders whose original exists (needs the delete grant). Run `find . -name "* 2.*"` after every cross. (Holonic Canvas, 2026-10)
- **`.fuse_hidden*` files collect in vault folders and get committed.** They are the device mount's leftovers of files deleted while still open (the MCP Reliability guide, 12.0, names them as the mount's tell). Add `.fuse_hidden*` to the repository's `.gitignore` (the Git Guide 2.0 template has the line) and untrack any already committed with `git rm --cached` in the operator's Terminal; the files stay on disk. One vault had 27 of them waiting for the next auto-commit. (DataWizard, 2026-10)
- **Git-ignore a backup of private data before the tool first writes it.** An auto-commit plugin set to commit every 15 minutes and push every 30 put a 36 MB database backup holding private chat text on GitHub within about half an hour; taking it back out needs a history rewrite. The rule: Conventions Registry, "Archiving" (10.0). (DataWizard, 2026-10)

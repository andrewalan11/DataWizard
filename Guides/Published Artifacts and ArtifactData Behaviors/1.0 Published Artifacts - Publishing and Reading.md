## Purpose

Runtime behaviors of published claude.ai artifacts (the Artifact tool: publish, read) and of an artifact's shared store (the ArtifactData tool and the page `db` capability). These are the gotchas that cost extra calls or silently lose data when an instance builds, republishes or feeds a published page. New artifact or ArtifactData behaviors append here rather than being re-derived.

**Scope.** Desktop-app Cowork artifacts (no URL, frozen data) and the chat-preview-vs-published routing rule live in **Cowork Build Environment** (Device Bridge section). Browser storage limits in embedded contexts live in **Browser and File System Access Behaviors**. Reading artifact links from a web context lives in **Chrome MCP and Web Tool Behaviors** (web_fetch Behaviors).

## Publishing

**Republishing needs a "viewed" read of the live source, and a `path` read does not count.** The live version counts as viewed when it is read in full: an `Artifact read` of the URL without `path` (brings the whole page into context), or every line of a saved copy read with the Read tool (about 25k tokens per Read call, so a 75 KB page takes two calls). Partial reads made before a refusal are not counted, and a read with `path: index.html` saves the page to a file but does not count as viewing it, and neither does `Artifact list` with `scope: files`. A republish therefore typically costs three calls: read, read, publish for a two-part Read of a 75 KB page, or three publish attempts when nothing was viewed first (next item). For a large page, budget the lead's own full read of the live source before the first publish: one page of about 4,800 lines took 19 chunked reads and about 170k tokens of context. A sub-agent's read does not count; only the lead conversation's own full read of the live source clears the gate. (Holonic Canvas, 2026-10)

**A refused publish saves the live source; diff it before you re-publish, then resend.** The first publish without a view is refused with a line diff and the live page's full source saved to a local file (path in the error); that refusal counts as the view. Diff the saved file against your base - if the live page holds only your base plus the publish skeleton, there is nothing to merge; if it holds someone else's edits, merge them first. Sending the same file again is refused once more as "identical content resent". What the third send does varies: two sessions saw it publish (sequence: refused, refused as unchanged, publishes; the second was a page whose local file already held all the live content), another saw identical resends refused for good with "Read it first". Do not count on the third send. A shell byte-compare of the saved copy (`cmp`, `diff`) does not count as reading it, and neither does an `Artifact read` with `path` (`index.html`); what reliably clears the loop is reading a small slice of the saved file with the Read tool (offset/limit, about 15 lines) and then publishing the same file. After a refusal that slice is enough; the full read in the previous item is what counts as the view before any refusal. (Holonic Canvas, Community Stack, LocationScout, 2026-10) On a large page, make the merge check before the first attempt instead: a `path: index.html` read saves the live page without counting as viewed, so strip the publish skeleton (recipe below) and compare the body byte for byte with your source copy (the page in git). Byte-equal means nothing was co-written and the refusal's diff will hold only your own lines, so the three-step can run without reading the page into context. When the change is small, merge from the saved file: take the live source from `<title>` to `</body>`, apply only the intended edit, and publish that. The live copy can differ from a fresh local build by the publish skeleton and by the key order of an embedded dict, so compare long lines by parsed JSON, not by text. (Holonic Canvas, LocationScout, 2026-10)

**Run the read sequence before the first publish, and the refusal does not happen.** Read the live URL with `Artifact read` (it saves the full HTML), byte-compare the live body with the source copy, read a small slice of the saved file with the Read tool, then publish with `url`. This was accepted on the first try, twice, and a second publish of the same file path later in the same session went through without a new read. A second case: on a 2.3 MB page the `Artifact read` returned the head inline and saved the full HTML to a tool-results file, and a 15-line Read slice of that file was enough for the republish to go through. (Community Stack, 2026-10; LocationScout, 2026-10)

**Publish recipe for a hand-built full-document page.** Strip the first 5 skeleton lines, the `</head><body>` and the trailing `</body></html>` the tool adds around the page, keep the theme with a one-line script, and smoke-test the page inside a fake artifact skeleton before publishing. Rendering it once locally is the one use the cloud container's headless browser is good for (see **Chrome MCP and Web Tool Behaviors**, Claude-in-Chrome section). To confirm the stripped copy matches what is live, `read` the artifact and compare: after the transform (strip the skeleton, keep the one-line theme script) the live inner HTML between the host's `<body>` and `</body></html>` matches byte for byte except one trailing newline the host appends. Compare that way before every publish, including a republish. (Evolutionary Media Commons, 2026-10)

**Mock up a design change as an overlay on a copy of the live page.** Read the published artifact, strip the host skeleton (first line and trailing `</body></html>`), then add a small exposed hook to the page's own API and an overlay script. That gave a working design mock-up in one session with no change to the build kit - good for "try it on one chapter first" asks. (Evolutionary Media Commons, 2026-10)

**A republish with `url` that omits `capabilities` keeps the page's declared capabilities** (for example `downloads`); pass the field only to change them. (Evolutionary Media Commons, 2026-10; LocationScout, 2026-10)

**A data-file-only republish still needs the page.** A `publish` with `url` and `files` alone is refused ("also pass file_path"). To change only a data file (for example a `canvas.json`), pass the unchanged page as `file_path` together with `files`; the viewed-read rule above applies to that page on the first such republish of a session. Afterwards, read `index.html` back with `path` and compare its sha256 with your pre-publish copy to confirm the page did not change. A read copy of the page carries the publish skeleton, so republish from your own source copy or strip the wrapper first (recipe above). (ReWoven, 2026-10)

**Multi-file publish: `files` sources must sit under the working directory or the scratchpad, and a Bash `cd` moves the working directory.** A site built in a folder under the container home was outside the (moved) working directory at publish time. Copying the site into the scratchpad and publishing with `root` set to that folder worked first time (16 files, one call). (MetaMyth, 2026-10)

**A page that saves itself rewrites its data file under you.** With the `artifact` capability in its files form, every save from the open page rewrites the data file. To merge new records in: re-read the data file right before merging, add records (never rebuild the file), check with a script that every old record is unchanged, then publish. A viewer with the page open gets a conflict on their next save and reloads - tell them to reload. (ReWoven, 2026-10)

**The session's safety check can deny a live-store write or a publish, even after earlier approval.** An `ArtifactData batch` to a live store was denied as "Modify Shared Resources" although the operator had approved it in chat; it passed when the operator approved it again in the session right before the call. An Artifact publish of a new page version was denied as "Production Deploy" and passed after the operator wrote an explicit go-ahead naming the publish ("yes, publish version 7"). Expect it on live writes and publishes: stop and ask the operator for an explicit go-ahead naming the action, never work around it. (Holonic Canvas, 2026-10)

**A publish refuses `.xlsx`, `.docx`, `.pptx` and `.zip` as supporting files, whatever `contentType` you pass.** The refusal lists the served types (html, css, js, json, txt, md, csv, svg, images, fonts, media, pdf). The route that worked on a mock page and in tests: publish the workbook as base64 text (`files/<name>.xlsx.b64.txt`); the page fetches it, decodes it to a Blob and calls the `downloads` capability's `save({filename, data})` (declare `downloads: true`; xlsx is on the save allowlist). A live click on the published page was still untested when this was written, so probe it before you promise the operator a download. (MetaMyth, 2026-10)

**The publish warning "page declares connector X but no successful call to it was observed in this session" is per session.** It appeared on a republish whose connector call had been proven live in an earlier session (a page button that starts a scheduled run through the `mcp` capability, owner only). The declaration was carried forward unchanged and the publish succeeded. Record where the call was last proven; do not read the warning as a sign that the integration broke; and do not re-test a connector that starts a real scheduled run just to silence it. (MetaMyth, 2026-10)

**A sub-agent can build and test an artifact page; the lead publishes it.** A strong-tier sub-agent built a page and tested it (Playwright in the container, files committed back to the device) but did not publish. The lead staged the built file, compared its md5 with the one in the sub-agent's report, read the live artifact in full, diffed, and published (the read gate above applies to the lead, not to the sub-agent). (ReWoven, 2026-10) In another session a cloud sub-agent built a 3.2 MB single-file page, and the lead published it with `publish_files` from the container path, in patch mode as `index.html`, with `base_version` from `get_artifact`; it worked first time. (LocationScout, 2026-10)

**A Docs-type artifact can be born with its full markdown, tables included, in one `batch` create call.** The call binds the document to the new artifact URL; the result shows `adopted: true` and `bound: true`. No separate write step is needed after the create. (LocationScout, 2026-11)

## Reading

**`Artifact read` needs the full `https://claude.ai/artifact/<id>` URL.** A bare `claude.ai/artifact/<id>` (or a bare id) is refused as "not an artifact URL". (Evolutionary Media Commons, 2026-10) `get_artifact` behaved the same way: it refused the short slug as "invalid slug" and accepted the full `https://claude.ai/artifact/<id>` link, which returned the UUID slug. (LocationScout, 2026-10) `publish_files` refuses the id from a claude.ai artifact page address in the same way ("invalid slug"); it needs the UUID slug that `get_artifact` returns for the full link. (ReWoven, 2026-11)

**A large read is saved to a tool-results file; only the head shows inline.** A ~700 KB page came back head-only, with the full HTML in a tool-results file; extract what you need (e.g. a baked data constant) from that file with a script rather than re-reading. An `Artifact` read of an artifact this session did not publish saves the full HTML to a local file (the result names it, as `.../tool-results/artifact-<id>-<version>.html`). Sub-agents in the same container can read that path, so a large page (an 870 KB deck here) can go to a reviewer agent without passing through the lead's context. (Holonic Canvas, 2026-10; ReWoven, 2026-10)

**A Slides-type artifact keeps its speaker notes in each slide's `<aside>`, not in the store.** The notes sit in `project/slides/<id>.html` (slide order in `project/deck.json`). The ArtifactData `notes` collection was empty in both decks read. Read all slide files in one `Artifact read` call with `paths`. (MetaMyth, 2026-10)

**`Artifact list` with `scope: "assets"` on another owner's artifact can return `not_found`, so `from_url` cannot copy its assets.** On a public artifact owned by someone outside the organization, `Artifact read` worked and saved the HTML, but the assets listing failed. A font that person had uploaded (served from `/_blob/...`) could not be copied with `from_url` + `asset_ids`. What worked: the operator downloaded the file, the session checked it (font check: Cowork Build Environment 10.0) and published it as a supporting file (`fonts/<name>.woff2`, contentType `font/woff2`). (MetaMyth, 2026-10)
